# Changelog

Notable changes to tsukkomi-mcp (Python package `self_directing_mcp`). Versions follow `pyproject.toml`. Releases before 0.6.0 are not itemized here; see the git history.

## 0.9.0 - 2026-10-16

**Highlights.** Four things since 0.8.0. (1) **The Grok CLI is a host**: a session provider `grok`, opt-in command hooks that deny a forbidden tool call the same way the Claude Code and AGY hooks do (Grok's tool names are rendered with Claude's vocabulary, so existing contracts apply), an installer that writes one file, and a Claude hook that stays silent on Grok's events; a call that a Grok hook refused is a rejected proposal in the audit, not an executed violation. (2) **Korean, Chinese and Japanese text is searchable**: sparse search no longer drops non-ASCII query words (issue #40), and a new index format, `sparse-v3.sqlite`, cuts runs of Hangul, ideographs and kana into overlapping two-character windows so any substring of two or more characters is found, including a word inside a compound. (3) **The compact sparse index loses the orphans** the store no longer holds. (4) **Contract authoring**: the fragility report of `upsert_contracts` now lists the host's file-read tools as missed spellings of reading a sensitive file, and the README documents the embedding endpoint (OpenRouter or a server of your own) and the language scope of the lexical index.

**Upgrading.** Restart every process that shares an index; a process on 0.8.0 ignores `sparse-v3.sqlite`, does not know the provider `grok`, and rejects a contract whose `provider` is `grok`, so upgrade all of them before registering such a contract. **Nothing happens to an existing index by itself**: `auto` keeps a sparse index that already holds data in its format. To get exact CJK search run `python -m self_directing_mcp.maintenance sparse-rebuild --format cjk` once per index, outside a request (minutes on a large index; the file is not used for answers until it is complete), then restart; going back is `SELF_DIRECT_SPARSE_FORMAT=compact`, and the older files are untouched. `sparse-rebuild` on the compact format now also deletes orphans. A Grok session is parsed by parser version 2 and the audit evaluator version is 9, so stored Grok parses and incremental states are re-derived once. Grok hooks are installed with `python scripts/install_grok_hooks.py --apply` (README, "Grok CLI"); nothing installs them for you.


**Highlights: the Grok CLI.** A new host, the Grok CLI (xAI; developed against 1.0.52), with a session provider and opt-in command hooks. The provider `grok` (parser version 1) reads `updates.jsonl`, the ACP update stream, and nothing else of a session directory (`chat_history.jsonl` and `system_prompt.txt` hold the rendered system prompt and are refused). The hooks (`scripts/install_grok_hooks.py`, `scripts/grok_hook.py`, `grok_hooks.py`) judge `PreToolUse` and `Stop` with the same `hook_policy` as the AGY and Claude Code hooks, from the six events `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure` and `Stop`, in one dedicated file, `<grok home>/hooks/tsukkomi.json`. A Grok call is matched in Claude Code's vocabulary (`run_terminal_command` is `Bash`, `read_file` with `target_file` is `Read` with `file_path`, `<server>__<tool>` is `mcp__<server>__<tool>`), so the contracts users wrote for Claude Code apply to Grok unchanged. Cut from this version, and listed as future work: input rewrite (`updatedInput`), output redaction (`updatedToolOutput`), the resident daemon, project-level `.grok/hooks` installation and following a `spawn_subagent` child session. Context injection at `SessionStart` and `UserPromptSubmit` is not offered because Grok discards it (its documentation: an allowing `UserPromptSubmit` has "no `additionalContext`", and an observe-only event reads only `systemMessage`).

**Highlights: the compact sparse index orphans.** The compact sparse index can now lose the documents the canonical store no longer holds. Such orphans never reached a search result (a search passes the canonical ids of its scope as `allowed_ids`), but nothing ever deleted them: they cost disk, made every filtered search scan more, and took part in the bm25 statistics, so a scope's scores differed slightly from those of an index that never held them. In one legacy `sparse.sqlite` of a long-used index more than a fifth of the documents were orphans, and a parser upgrade or a re-index can leave some in `sparse-v2.sqlite` too. `python -m self_directing_mcp.maintenance sparse-rebuild` now deletes them, and so does a `sparse` or `hybrid` search over all sessions. The legacy file is still never read or written.

**Highlights: the CJK sparse index.** Sparse search finds a Korean, Chinese or Japanese word wherever it sits: `회의` inside `원탁회의를`, `색인` inside `v2색인`, a word in an unspaced Chinese or Japanese run. The compact index stored one token per space-separated run, so even after the Korean query fix ([#40](https://github.com/fox1245/tsukkomi-mcp/issues/40)) only the start of a run could be found. A new format, `sparse-v3.sqlite`, rewrites every run of Hangul, CJK ideographs and kana into overlapping two-character windows before FTS5 sees the text, and a query for a run is the phrase of its windows. It is a new file next to the old ones, which are never touched; a fresh install gets it, an existing index keeps its file until you build it with `sparse-rebuild --format cjk`. The price is a bigger file (1.5 times the compact one on the synthetic Korean-like benchmark), one more rebuild, and the limits listed below.

- **A Grok call that a hook blocked is a rejected proposal** (Grok parser version 2, evaluator version 9). A `PreToolUse` denial used to leave the call an attempt, so the history audit, the `Stop` note and `audit_session` reported a `must_not` match for a call that never ran. Now such a call is listed in the finding's `proposals_rejected` (`denied_by` is the source the host names, `denial_event_id` the host's note), is not an executed match, and the audit is `clean` ("no executed forbidden match ...") when every match was blocked; the `Stop` note puts it on its own part ("Rejected by the host, not executed ..."), as for Claude Code and AGY. Only the host's own record counts. Grok writes a `hook_annotation` of kind `tool_outcome`, "`<tool>` blocked by <source>: <reason>", which has no call id; the failed update's "Hook denied: <reason>" is a hook's text and, like a message, a tool output or a thought, is never read for it. Four live headless runs (Grok 1.0.52, nine denials) show that Grok numbers its records (`_meta.eventId`) and that a denial takes four consecutive numbers (the call n, the hook's report n + 1, the failed update n + 2, the note n + 3), **but that the file shows the hook's report and the note before the call and its update** in all nine, with other records between them for parallel calls. So the note does not "directly follow" the update in the file.
- **How the note and the call are joined** (`src/self_directing_mcp/audit/hostblocks.py`, `HostBlocks`). The parser links nothing and keeps every record independent: a failed result carries `host_event_id`, the note becomes a small runtime event (`evidence_origin: host_tool_outcome`, `host_event_id`, `blocked_tool`, `denied_by`; the reason a hook wrote is not kept; it never splits a streamed message). The audit joins them in either file order and across any read boundary: a call is blocked when its `failed` result is numbered one less than a note that names the call's own `native_tool_name`, within 512 events, the call is the only one with its id and has one result. The reference evaluator feeds the class every event (`runner.blocked_calls`); the incremental evaluator keeps the same class whole in its shared facts (`GrokFacts`, persisted, bounded, `NeedFull` past 2048 blocked calls), so the two cannot differ on the rule. Anything not unambiguous is an attempt: no note, another tool, numbers not one apart, two notes or two updates with one number, a call with two results or a shared call id, a result that is not `failed`, a stale note, a note in a message or a tool output, a record of another session or without a number, and a user-rejected or cancelled call (no shape is recorded for it). Rejected: deciding in the parser. A parser can only wait for the other half of the pair by returning an earlier offset, and every read that ended between the records would then leave an unread tail (`sync_in_progress`, incomplete coverage, a clean absence proof turned into unknown) and a note whose call never arrives would hold it for good; a look-back past the cursor would read bytes the capture guard has not vouched for. `ingest._AUDIT_META` carries the four keys the join reads on Grok's slim audit events.

- **Orphan deletion in `sparse-rebuild` / `SelfDirectEngine.rebuild_sparse()`.** After it has written the missing documents (a missing document makes a search incomplete, an orphan only costs space, so a budget that runs out leaves the more useful index) it deletes the compact index's documents whose event the store lacks, 500 per transaction, under the same `--budget-sec`, interrupt and resume rules: running it again continues, and a finished index is not written at all. The result (and the command's JSON line) reports `orphans`, `orphans_removed`, `orphans_spared` and `orphans_remaining`; progress for the deletion goes to stderr (`rebuild_sparse(orphan_progress=...)`), and the "stopped by" message names the extra documents left. The bm25 statistics are corrected in the transaction of every delete (`verify_statistics()` holds afterwards, and results and scores equal those of an index that never held the orphans, tested on a seeded corpus with multi-token queries).
- **A document the store holds is never deleted.** Both id sets come from one snapshot taken under the publication guard and every batch asks the store again (`store.existing_ids`) under the guard right before it deletes: an event that a sync published after the snapshot is kept and counted in `orphans_spared`. The ids are compared with the whole store, not with the searched provider's.
- **Global `sparse` / `hybrid` search repair.** Besides writing what its scope lacks, a search over all sessions (it already scans the index's ids) deletes the orphans, after the fill and before it searches. It is housekeeping: it stops after 2 seconds or a quarter of the time the request has left (whichever is less) and when the index is busy, and the search still answers; every finished batch is kept and the next global search (or the rebuild) continues. A cancellation or the request's own deadline ends the request, as for the fill. When the counts show nothing extra it costs one cached count. A search of one session does not delete: the compact file has no index on a document's session, so listing one session's ids would scan the whole id map on every such search.
- `audit_status.sparse_extra_ids`: `max(0, sparse_counts.compact - total_chunks)`, from counts the status already had (no scan); a lower bound while the compact file lacks documents, `null` without a compact file.
- `CompactSparseIndex.delete_ids` returns the number of documents it removed; `scripts/bench_sparse.py --stages orphans` times the deletion.
- Tests: `tests/test_sparse_orphans.py` (removal by the rebuild and by a global search; parity with an index that never held the orphans, ids, ranks and scores; `verify_statistics()`; a tiny budget, an interruption, a busy index and a killed process, each resuming to the same end with the removals adding up; an idempotent second run that writes nothing; the legacy file byte-identical after every operation; the delete set taken under the publication guard; an event that arrives meanwhile kept, in the rebuild and in a search; another provider's documents kept; no extra work for a consistent index; `audit_status`; the command; and seven mutations that the scenario must catch: a deletion that removes a live id or another provider's documents, skips the statistics correction, ignores a budget, touches the legacy file or deletes nothing). - **Contract fragility report: reading a sensitive file with a host's file-read tool** (library 1.1.0: 13 families, 214 variants and 44 canonical spellings; was 10, 158 and 25). A contract written for "never print the secrets in `.env`" is often shell-scoped, for example `(cat|head|tail|less)\s+\S*\.env`. A host's file-read tool is not a shell command: the call the contracts are matched against is `[tool_call:Read] {"file_path": "/work/.env"}` (Claude Code), so that regex never matches it, while a regex that names the file matches any tool. The report now lists such calls as missed spellings. Informational only, like the rest of the report: no contract, regex or verdict changes, the `MAX_*` limits are unchanged and hook paths still do not import the module.
- **File families, one per file.** A regex about one file is not told about the spellings of another. `read_secret_file` (`.env`) already existed with shell spellings only; a second `.env` family would have reported the same file twice, so it was extended instead: its standard spellings are now `cat`, `head`, `tail`, `less` and `more` (`head .env` was a non-standard spelling before), and it gains `cp`, `source` and `.` as readers. New families: `read_env_production` (`.env.production`), `read_ssh_private_key` (`~/.ssh/id_rsa`) and `read_aws_credentials` (`~/.aws/credentials`), the files a "do not print secrets" instruction most often names. Each has the same five readers as standard spellings, other shell readers (`sed -n`, `awk`, `grep`, `cp`, `xxd`, `base64`, `python3 -c`, the `$HOME`, absolute-path and `cd` spellings, PowerShell and cmd readers, and for AWS the CLI's `configure get` and `export-credentials`) and three tool-call spellings. All new entries are `verified: false`. Not added: another key file such as `id_ed25519`, which would be a family of its own.

- **Selection is unchanged: a family is reported only if the regex matches one of its standard shell spellings.** `(cat|head|tail|less)\s+\S*\.env` is reported for `read_secret_file` with the Claude, AGY and OMP calls listed among its missed spellings (plus `more .env`, the standard spelling it does not name). `(?s)\[tool_call:[^\]]+\].*\.env` matches only tool-call text, selects no family and reports nothing; `\.env` selects the family and misses none of the three calls. Matching is a substring search, so a regex that names only the `.env` prefix (`cat\s+\.env`) also matches the `.env.production` standard spellings and is reported for both families (`.env` first); `\.env(?![\w.])` ends the name and stays with `.env`, and a regex about `.env.production` is not told about the `.env` family. This is documented in the README and covered by tests rather than changed, because the matching must stay what the audit does. A capped list (8 per family) now counts every tool call as a technique of its own, so all three host spellings are listed together; families without tool calls list exactly as before.

The README's fragility section lists the new families and the file-read point; the report's note says that tool-call spellings are matched as the text of the call.

- **The CJK sparse index format** (`sparse-v3.sqlite`, `sparse_meta.format` `compact-cjk-1`, `tokenization` `cjk-bigram-1`, `state` `building` or `ready`; `CjkSparseIndex` in `index/sparse.py`, a subclass of `CompactSparseIndex`, and `index/cjk.py`). The same contentless FTS5 table, `porter unicode61` tokenizer, id map, exact bm25 statistics and `verify_statistics` as the compact format; the document length that `_retire_statistics` retires is the token count of the rewritten text that was indexed. Write side: `cjk.pretokenize` runs after `mask_secrets` (standard library only, `re` and `unicodedata`; the hook processes import this package, nothing heavy). NFC first (not NFKC: fullwidth Latin is not folded); a CJK run is a maximal run of Hangul syllables, jamo, compatibility jamo and jamo extended A and B, CJK ideographs (extension A, unified, compatibility, the supplementary planes up to extension H) and the iteration mark U+3005, Hiragana, Katakana (with the phonetic extensions) and halfwidth Katakana; fullwidth ASCII, the Katakana middle dot U+30FB, U+30A0, ideographic punctuation, radicals and strokes end a run. Zero-width characters (U+200B to U+200D, U+2060, U+FEFF) between two run characters are removed so that they do not cut it. A run of n >= 2 characters becomes a space, its n-1 windows separated by single spaces, and a space: **the outer spaces are what let `색인` find `v2색인`** (without them `v2` and the first window stay one token). A run of one character becomes a one-character token. Text without any run character is returned as the same string, so it is indexed exactly as in the compact format. Every code point of the run class is a token character of `unicode61`, so a window is never cut by the tokenizer itself (a test checks all 114,660 of them against the running SQLite; the same probe gave the same answer on SQLite 3.45.1, 3.50.4 and 3.53.1).
- **Queries on the CJK format** (`_fts_query_cjk`; the query builder of the Korean fix is unchanged and stays for the legacy and compact formats). The query is put in NFC; a query with no CJK run gives exactly the string `_fts_query` gives (an ASCII-only query is byte-identical, and on an ASCII-only corpus the ids, ranks and scores equal those of the compact format); a CJK run of two or more characters is the quoted phrase of its windows (`색인을` is `"색인 인을"`; a run longer than 33 characters keeps its first 32 windows); a one-character run is the prefix term `"집"*` over the windows; the other tokens are the exact terms of the old builder; terms are joined by `OR`; at most 24 terms come from CJK runs, a repeated run counts once. Quotes and operators cannot reach the MATCH string (fuzzed through a real FTS5 table).
- **`SELF_DIRECT_SPARSE_FORMAT=cjk`**, validated identically by `config.Settings` and the hook reader (`auto`, `legacy` and `compact` work as before). `auto` uses `sparse-v3.sqlite` when its state is `ready` and its tokenization is known, and creates it on a fresh install (no sparse file holds a document); it never starts it over an index that already holds data in `sparse-v2.sqlite` or `sparse.sqlite` (a legacy-only index moves to the compact file as in 0.8.0), and it never searches a file in state `building` or with an unknown tokenization: a visible fallback to the compact format (`degraded_flags` has `sparse_cjk_unavailable`), where an explicit `cjk` raises `SparseFormatError` naming the repair. No tokenization is substituted for another and no older file is read for results, written or deleted. The runtime probe (`compact_support`, SQLite 3.43 or newer) applies as for compact: an error for `cjk`, the legacy fallback for `auto`.
- **`sparse-rebuild --format cjk`** (and `SelfDirectEngine(sparse_build=True)`, `open_sparse_index(..., build=True)`) builds `sparse-v3.sqlite` from the canonical store, bounded and resumable like the compact conversion. The new file is in state `building` until the end: after the batches the command takes a catch-up pass over the events published meanwhile and then, under the publication guard, compares the canonical ids with the index's and sets `ready` in one transaction only when the document count equals the store's (`CjkSparseIndex.finish_build`); if events keep arriving it ends partial (`stopped_by: "catch_up"`, exit status 3). A killed or stopped build is finished by running the command again, with or without `--format` (it ends equal to an uninterrupted build: same ids, ranks, scores and statistics); a file that is already `ready` is only topped up, never demoted. The JSON result gains `tokenization`, `index_state`, `catch_up_written` and `catch_up_removed`.
- **`audit_status`**: every entry of `sparse_files` now has `path`, `tokenization`, `state` and `documents` besides `name`, `format`, `active`, `exists` and `bytes`, and lists the third file; `sparse_counts` gains `cjk`; new `sparse_format_choice` (which file `auto` chose and why) and `sparse_cjk_hint` (for example `sparse-v3.sqlite is not built: run python -m self_directing_mcp.maintenance sparse-rebuild --format cjk ...`); `sparse_extra_ids` is computed for the compact-family file in use; the degraded flag `sparse_cjk_unavailable`. The existing fields stay.
- **Limits of the CJK format, all tested and in the README.** A query of one character is a prefix query that **misses a document where the character only ends a run** (`이사집` holds the windows `이사` and `사집`, so `집` does not find it; `사집` does). **Run-boundary false positives**: FTS5 phrase adjacency ignores what separates two tokens, so two neighbouring runs whose border windows form the query's windows match (`버스 스톱` matches `버스톱`); a document that contains the substring is never missed and every extra is such a coincidence (a seeded property test checks both against substring containment, with NFD, zero-width characters, punctuation and Latin glued to Hangul in the corpus). It is a substring search, not a word search (`회의` also finds `회의록`), with no whole-word boost. Halfwidth Katakana and fullwidth Latin are not folded (NFC, not NFKC); an ideographic variation sequence ends a run. The file is **bigger than the compact one for CJK-heavy text**, **one more `sparse-rebuild` is needed** to adopt it on an existing index, and **a query on a window that occurs in nearly every event costs more**.
- **Measured** (`scripts/bench_sparse.py --stages cjk --events 100000`, new: a seeded corpus of invented Korean-like words, 43.3 MB of text, SQLite 3.53.1; the compact format against the CJK format on the same events). File: 23.5 MB (0.54 of the text) and 6.0 s to build against 35.5 MB (0.82; 1.5 times) and 11.4 s; pre-tokenization 0.04 ms an event. Top-20 p50 (events found): a two-character word in nearly every event 112 ms (99,264, its prefix term) against 56 ms (99,264); the same word with a particle 115 ms (99,264: the stem's prefix) against 14 ms (16,743, exactly the events that contain it); a rare word 0.37 against 0.23 ms (229); an inner piece of a longer word 0 events against 69,409 in 35 ms; a whole three-character word 53 against 50 ms (69,409); a one-character query 99,329 of the 99,342 events that contain the character (13 end a run) in 68 ms; a Latin word 1.18 ms in both. The same measurement at 3,000 events and the corpus itself are in `tests/test_bench_sparse.py`.
- Tests: `tests/test_sparse_cjk.py` (the pre-tokenizer: identity on text without a run character (paths, code, emoji, fullwidth Latin, accented Latin in both normalizations, the middle dot, ideographic punctuation, radicals), the outer spaces, one-character runs, mixed kana and kanji, halfwidth Katakana, NFC/NFD equivalence, zero-width removal, every code point of the run class against a real FTS5 tokenizer; the query builder: examples, the 32-window and 24-term caps, ASCII byte-identity, injection fuzzing; real FTS5 round trips for a two-character word, a word with a particle, an inner piece of a compound, `색인` in `v2색인`, unspaced Chinese, kana, the one-character prefix query and its documented miss, Latin and mixed queries; the seeded property test; exact statistics after deletes and re-upserts against a from-scratch index; size and time guards) and `tests/test_sparse_cjk_formats.py` (`auto` in each situation, `building` and unknown tokenizations never answered from, an old SQLite, rebuild resumption and the catch-up pass, `ready` only when the counts agree, the rebuild command, `audit_status`, the older files byte-identical after every operation, `search_history(mode="sparse")` through the real engine finding an inner word the prefix fix cannot). ### Fixed

- **`scripts/claude_hook.py` is silent on Grok payloads.** Grok loads Claude Code's settings file by default, so an installed Claude hook was also run on every Grok event, rejected the Grok transcript (outside the Claude projects root) and printed "Tsukkomi check FAILED (PathTraversalError)" on every tool call, about 0.45 s each, without protecting anything. The script now recognises a Grok payload before it imports the package or touches the daemon (stdlib only: a transcript path with a `.grok/sessions` segment in either slash style, or Grok's camelCase envelope with no `.claude` transcript path) and answers with silence: nothing printed, nothing written, no `hook_health`, exit 0; `claude_hooks._dispatch` and `main` hold the same defence. The bypass costs about 6 ms over a bare interpreter (a 13 ms start; 19 ms for the whole hook; medians of 40 runs). A real Claude Code payload behaves as before.

- **Sparse search finds Korean text ([#40](https://github.com/fox1245/tsukkomi-mcp/issues/40)).** `search_history` with `mode="sparse"`, and the sparse half of `hybrid`, built its FTS5 query from `[A-Za-z0-9_-]+` only, so a Korean query returned nothing while `mode="regex"` found the text (both index formats, since before 0.8.0). `_fts_query` (`index/sparse.py`, shared by `SparseIndex` and `CompactSparseIndex`) now handles it on the query side alone: the stored index, its tokenizer, both file formats and the dependencies are unchanged, so there is nothing to rebuild. The rules: the query is put in NFC first (not NFKC, which would fold fullwidth Latin) and lengths count NFC characters; tokens are runs of `[\w-]`; **a query of ASCII only gives exactly the string it gave before** (one-character tokens skipped, duplicates and `foo-bar` kept, no cap); a non-ASCII token of another script (`café`, Cyrillic, Greek) is an exact quoted term, folded by unicode61 like the stored text (it used to be cut into its ASCII fragments: `naïve` was `"na" OR "ve"`); a token with Hangul, CJK ideographs or kana is split on `-` and `_` and each part becomes a prefix term `"색인"*`, because the index stores a Korean word with its particle as one token (`색인을`, so the exact `"색인"` finds nothing), except a one-character part, which stays exact (`"집"`); a word of Hangul syllables that ends in `에서 으로 에게 까지 부터 을 를 은 는 의` and keeps at least two syllables also searches its stem, never instead of the word (`색인을` is `"색인을"* OR "색인"*`; `이 가 도 로 와 과 만 에` are never cut because they end real nouns such as 도로, 어린이, 비만); a query has at most 8 prefix terms, the stems counted, the words first in query order, and a word beyond them is an exact term; the same non-ASCII word typed twice is one term. **Limits:** a prefix term also matches longer words (`색인` finds `색인표`) and BM25 does not rank the exact word above them; Chinese and Japanese, and Korean written without spaces in a code-mixed run (`v2색인`), are one stored token per unspaced run, so a query matches from the start of the run only and an inner word needs `mode="regex"`; a particle that is not in the list is not cut; a one-syllable word is exact, so `집` does not find `집에서`. **Cost**, from `scripts/bench_sparse.py --stages korean` (a seeded synthetic corpus of invented Korean-like words, 100,000 events of 40 tokens, 3,000 stems with Zipf frequencies and 40 particles and endings, compact format, SQLite 3.53.1; p50 of 15 timings of the ranked top 20 without a filter, two runs): for a frequent stem (in 66,923 events as the bare word, in 99,264 with any ending) the exact term took 34 to 43 ms and the prefix term 114 to 125 ms (a typed stem plus a particle, which searches the word and its stem, 122 to 129 ms); for a rare stem (48 and 229 events) 0.11 to 0.13 ms exact and 0.32 to 0.33 ms prefix (0.43 to 0.53 ms for the word-and-stem pair). So a prefix on a very frequent stem costs several times an exact match (three to four times here; a raw FTS5 run in which most occurrences of the frequent stem carried an ending measured 19 ms against 157 ms) and grows with the number of events that contain any form of the stem; on a rare stem both are under a millisecond. A search with `allowed_ids` was not timed separately. Tests: `tests/test_sparse_korean.py` (the old builder copied as the reference and compared byte for byte on fixed and seeded random ASCII queries; every rule above; the issue's repro on both formats with identical ids, scores and ranks; the filters; operator characters never reaching the MATCH string; `search_history` in `sparse` and `hybrid` mode against `regex`), `tests/test_bench_sparse.py` for the new stage; both join the CI lists.
- **A Grok `Stop` note no longer calls a contract violated for a call that a hook blocked and that never ran** (see "A Grok call that a hook blocked is a rejected proposal" above). Limits: it rests on four short recordings of one Grok version, so an ordering or numbering that differs in another version, a permission rule's or the user's refusal, and a managed hook's note (documented, never seen) leave the call an attempt, as before. Raising the parser version reparses each indexed Grok session once on its next sync or audit.

### Upgrading

- **Restart every process that shares an index.** A process on the older code ignores `sparse-v3.sqlite` and the setting `cjk` (the older setting values are validated as before).
- **An existing index changes nothing by itself.** With documents in `sparse-v2.sqlite` or `sparse.sqlite`, `auto` keeps that file. To adopt the CJK format, once and outside a request: `python -m self_directing_mcp.maintenance sparse-rebuild --format cjk` (bounded, resumable, progress on stderr, about as fast as the compact conversion plus the pre-tokenization). While it runs the file is in state `building` and no process searches it; when it ends `ready`, `auto` uses it. `audit_status` shows `sparse_files[].state` and `documents`; when `documents` of `sparse-v3.sqlite` equals `total_chunks` and every process uses the CJK format, `sparse-v2.sqlite` can be deleted by you (the program never deletes it).
- **Rollback:** set `SELF_DIRECT_SPARSE_FORMAT=compact` (or `legacy`). The older file is used as it was; `sparse-v3.sqlite` is left where it is.
- **Which to use:** the CJK format for histories with Korean, Chinese or Japanese text; for English-only histories the CJK file has the same size and the same results as the compact one.

## 0.8.0 - 2026-10-16

**Highlights.** Three results of the storage roundtable ([#33](https://github.com/fox1245/tsukkomi-mcp/issues/33)): portable contracts (the bullets that start with that name below), a compact sparse index (the next paragraph) and a third dense backend, PostgreSQL with the pgvector extension, behind the existing `VectorIndex` interface, as an opt-in extra. SQLite stays the default and the canonical store, the default install needs neither Docker nor PostgreSQL, and no backend is ever substituted for another.

**Highlights: the sparse index.** The sparse (FTS5) search index is about 70 % smaller with identical search results. It was the largest file of an index (a Codex index of 365,768 events: 4.6 GB of 7.0 GB) because its FTS5 table stored a copy of every masked text that no query ever reads back. The new compact format (`sparse-v2.sqlite`) is a contentless FTS5 index: on synthetic 100,000-event corpora it is 269.1 MB instead of 918.8 MB (Codex-like, 5.6 KB of text per event) and 98.0 MB instead of 321.3 MB (OMP-like, 1.6 KB), with the same ranked ids and the same BM25 scores for 200 benchmark queries (single and multi-token, hyphenated, Korean, no-match, session and `allowed_ids` filters, `top_k` 5/20/100) before and after deleting and re-inserting 1,000 events (100,000-event corpora on SQLite 3.53.1, 20,000-event corpora also on 3.45.1). Searches with a session filter are 7 to 30 times faster. Measurements: README, "Sparse index formats"; `scripts/bench_sparse.py`.

**Upgrading, the sparse index.** Restart every process that shares an index. The default `SELF_DIRECT_SPARSE_FORMAT=auto` uses the new file `sparse-v2.sqlite` when the running SQLite is 3.43 or newer. The old `sparse.sqlite` is **never** read for results, written, truncated or deleted by the program: it stays where it is, taking its space, until you delete it. The new file starts empty and fills like any missing derived index (a sync writes the sessions it syncs, a `sparse` or `hybrid` search writes what its scope lacks), so convert the whole index once, outside a request: `python -m self_directing_mcp.maintenance sparse-rebuild` (bounded, resumable, progress on stderr; about 1,100 events a second). `audit_status` then shows `sparse_files` and `sparse_counts`; when `sparse_counts.compact` equals `total_chunks` and no process uses the legacy format any more, stop the processes and delete `sparse.sqlite`. `SELF_DIRECT_SPARSE_FORMAT=legacy` keeps the previous format.

- **Journal mode of the authority databases: measured, opt-in, not the default** ([#18](https://github.com/fox1245/tsukkomi-mcp/issues/18) R1). `SELF_DIRECT_SQLITE_JOURNAL=delete|auto` (default `delete`, the rollback journal as before; `config.Settings`, `settings_core.FIELDS` and the parity table validate it identically) selects the journal mode of `meta.sqlite` and `agy-receipts.sqlite`. `auto` uses write-ahead logging only where `journal.choose_journal(path)` positively identifies a local file system (Linux: `os.statvfs` plus `/proc/self/mountinfo`, allow-list ext2/3/4, xfs, btrfs, tmpfs, f2fs, zfs and an overlay whose upper directory resolves to one of those; `9p`/`drvfs`, `nfs*`, `cifs`, `smb*`, `fuse*` and `virtiofs` are denied; anything undeterminable is unknown; Windows: a fixed drive by `GetDriveTypeW`, never UNC, device paths or mapped network drives). **Unknown means DELETE**, which is the old behaviour and not a claim that DELETE is safe there. `synchronous=FULL` is set explicitly on every connection and `NORMAL` is never used for events, cursors or receipts. - **Slice commits: a sync that cannot finish inside its budget keeps what it parsed** ([#26](https://github.com/fox1245/tsukkomi-mcp/issues/26), roundtable 8: P1, P3, P5, P7, P8). A cold or appended source whose sync did not fit the request budget (8 s for hooks, `audit_session` and `check_action`, 45 s for the other tools) was parsed until the hard deadline, rolled back, and started again from zero by the next call, so repeating the call made no progress. Now the parse ends at a record boundary once its soft deadline (`now + 0.5 * remaining / 1.3`, at least 0.25 s; at least 256 records **and** 1 MiB of progress even when the time is already spent) passes, and the prefix it read is published in one transaction like any other append (events, cursor, block table and metrics together); the next call continues from the cursor. The one place that decides is `session_events.iter_raw_lines`, which consults a request-scoped `slice_budget.SliceBudget`; the five parsers are not modified (`tests/test_slice_equivalence.py` shows they do not need to be: a session synced in slices, with seeded forced stops of 1 to N records, capture caps and stops across 1 MiB block boundaries, holds row for row what the one-shot sync holds, for Codex, OMP, AGY with hook receipts and a sibling full log, Claude Code and Grok Bot, including the derived index and an audit; the one parser memory that a slice boundary loses, the agent-id consistency check of a Claude Code subagent file, is pinned as a strict `xfail`). `SELF_DIRECT_SYNC_SLICING=auto|off` (default `auto`; `off` is exactly the all-or-nothing sync of before) and `SELF_DIRECT_SYNC_SLICE_BYTES` (default 64 MiB) are validated identically by `config.Settings` and the hook reader, and slicing is on only for a request with a finite deadline and a plain file.
  - **Never over an index that exists.** A parse that replaces events (parser upgrade, a source whose stored hash no longer matches, changed AGY receipts, another path) is never published in pieces: it is replaced in one transaction, so an interrupted re-index leaves the previous events, ids, anchors and vectors untouched (the next entry keeps its progress in a spool until that one commit). The capture of a source that is far from indexed is cut at the last record inside `cursor + SELF_DIRECT_SYNC_SLICE_BYTES` (at least one whole record; it behaves exactly like the capture of a shorter file); one that then turns out to need a re-index is taken again whole without spending a recapture attempt. A cursor with an outdated parser version is not cut at all. `.jsonl.zst` sources are never cut.
  - **What a stop verifies.** At an early stop `iter_raw_lines` still verifies what it consumed against the capture (`guard.finish`). A stop inside a block has no capture digest of the partial block, so the rest of the block is read back and the whole block is compared with the capture's digest of it (plain-digest cursors: the consumed bytes plus the rest of the capture against the digest of the capture's last record, after which the offset is a verified checkpoint); a byte changed between the capture and the parse is `SourceChanged`, not evidence (`tests/test_slice_capture.py` fails without it).
  - **Response, additively.** `sync_session` (a call with a deadline) returns `sync` = `{state: "partial" | "complete", indexed_through, pending_bytes, target_bytes, progress (the committed share), retry_after_ms (a hint, 500 while partial; nothing retries automatically), stopped_by: "soft_deadline" | "slice_cap" | "eof"}` and a `nudge` that says what to do. `coverage` gets `backlog_bytes` and the issue `sync_in_progress` (next to `unread_bytes`) while the capture holds records the index does not, and is not `complete`. The evaluator's rules are unchanged: the extra issue is what keeps `judged_prefix` (reserved for pure append) from being set, so a partial prefix is never `clean`, a forbidden match in it is a `violation`, a proposed prohibited action is a `violation` whatever the backlog, and an obligation or the absence of a match is `unknown` (`tests/test_slice_convergence.py`).
  - **Single flight with a bounded wait.** A request that may slice waits for the session's flight at most `min(1 s, a quarter of its time left)` (`session_flight(max_wait=...)`; for `audit_session` and `check_action` the time left is the sync's 60 % share), so a heavy-call slot is never held idle behind a leader that is committing slices; `_refresh_evidence` then judges on the committed prefix (the existing failure branch, issue `sync_in_progress`), and a direct `sync_session` is answered with an incomplete response whose `error` is `sync_in_progress` (a private `FlightBusy`, an `IndexBusy`). A real deadline overrun still says `request_deadline`. The statistics know the reason: such an answer, and a `sync_session` that ended partway, count as `degraded` / `sync_in_progress`, a busy `sync_session` as `incomplete` / `sync_in_progress` (the closed vocabulary of `request_stats.REASONS` gained the name). Without slicing the wait is what it was. **Reasons and issues are an open set:** the OMP extension, the Codex hook and the AGY and Claude Code adapters show them as opaque strings (`tests/test_slice_adapters.py` feeds each the real answer of a partially synced session), and clients outside this repository should too.
  - **Measured and tested.** `scripts/bench_slicing.py` (synthetic, seeded, deletes its temporary directory): calls to converge and per-call wall time for budgets of 1, 4 and 8 s on 100,000 and 300,000 events, total CPU against a one-shot sync, capture time against the number of slices, and the cost of the stop checks when no stop happens; the numbers are in the pull request. Fault injection stops a sliced sync at every one of its cooperative checks (all of them for Codex, a sample for the others) and a subprocess is killed with SIGKILL at several moments; the index verifies, ends on a record boundary whose hash is that of exactly that prefix, keeps the previous events, and a later sync completes to the one-shot index (`tests/test_slice_faults.py`); a request stopped right after a slice was committed loses its answer and not the slice (the next call goes on from the cursor). The new tests run in the smoke job and the Linux regression job. See [Large sessions and deadlines](README.md#large-sessions-and-deadlines), including what it does not do: the evaluation is not sliced (two entries on, what it is sized by), and a re-index is staged rather than sliced into the index (next entry).
- **Re-index in a parse-ahead spool: a re-index that cannot finish inside its budget keeps its progress** ([#26](https://github.com/fox1245/tsukkomi-mcp/issues/26), roundtable 8, P2; AGY and Claude chose it, Codex dissented for a generation pointer). A parser upgrade (the AGY parser is at 8 and the Claude Code parser at 3: every session of those providers is reparsed on its first sync), a source whose stored hash no longer matches, changed AGY receipts and a retried truncated fallback make a sync parse a session from byte 0 and replace its events in one transaction, which for a session that does not fit the request budget was all or nothing: every call parsed until its deadline, rolled back, and started again. Now a request with a finite deadline that syncs a plain file **stages** the parse slice by slice in `<index dir>/reindex/<provider>-<session key>.<target parser version>.spool` and publishes it with ONE ordinary `replace` commit; the index is not touched until then, so an interrupted or crashed re-index leaves the previous ids, anchors, cached vectors, cursor and block table exactly as they were, and audits keep judging the previous events with `parser_outdated` (or `source_changed`), `complete` false and never `clean`. `_commit_rows`, the schema and every read query are unchanged.
  - **The spool** (`reindex_spool.py`, standard library only). A header frame, then per slice its row frames, the ids/flags/tallies the commit needs, what the next slice's parse needs from this one (OMP: the earliest byte of every tool call; AGY: the receipts the events were derived from) and a trailer frame `{slice_seq, start, source_offset_end, rows, rows_total, prefix_hash}`; frames are `[length][crc32][payload]`, the rows reach the disk before the trailer that names them (`fsync`), the progress is the last valid trailer, a torn tail is cut at the next open and a slice that is staged twice writes nothing. The directory is 0700 and the file 0600, a symlink or another user's directory is refused, one writer at a time (`fcntl.flock`; `msvcrt.locking` of one byte beyond the data on Windows, where only the uncontended case is covered by the smoke job), and no spool is started when the index volume has less than 9 times the source size free (`reindex.state: "disabled"`, reason `disk`: that request is the re-index of before). It is a second copy of the session text, in the index's trust domain; it is deleted when its commit succeeds or anything it was built on changes, and a spool of another session is never touched.
  - **What discards it** (the spool, never the index; the staging starts over from byte 0 in the same request): another spool format, target or base parser version, an index whose cursor was rewritten since (including another process finishing the re-index), another source file or a changed head, a source shorter than the staged range, a changed prefix hash at the staged offset, AGY receipts that changed in a way that affects an event already staged (a receipt for a later step does not restart a session that is still being written), a checksum that fails, an unreadable header, and the room on the volume. The evaluator version is not part of the binding. Orphans (a spool for a target version at or below the stored one, one with an unreadable header, one a crash left after its commit) are deleted by the next sync of their session.
  - **One commit, only when it fits.** When the staged range reaches the end of what the request's own capture observed (that capture is the verification of `[0, target)`), the sync commits once; a re-index that is parsed whole in one call and whose commit fits is published from memory as before and never makes a file. The commit is one transaction that cannot be cut, so it is started only if `18 microseconds * rows * 1.5` fits in 90 % of the time left (`ingest.COMMIT_SECONDS_PER_ROW`, `COMMIT_SAFETY`, `COMMIT_RESERVE`); otherwise the spool is kept and the answer is `ready_to_commit`. The wall is about 160,000 events for a hook's sync and about 1.5 million for a `sync_session` of 45 seconds (an explicit `sync_session` takes the same path, finishes the commit when it fits, and its `nudge` says what to do).
  - **Response, additively.** `sync.reindex` = `{state: "staging" | "ready_to_commit" | "committed" | "discarded" | "disabled", staged_through, target_bytes, rows, reason}`; while a re-index is staged `sync.state` is `partial`, `indexed_through` is the previous cursor, `progress` the staged share, `reindexed` false and `reindex_reason` says why one is under way. `coverage` keeps its old issue and adds `sync_in_progress` (staging) or the new `reindex_ready_to_commit` (everything staged, commit not attempted); the closed vocabulary of `request_stats.REASONS` has the new name and a result that names it is counted `degraded` with it. Reasons and issues stay an open set.
  - **Measured and tested.** `scripts/bench_slicing.py --reindex` (synthetic, deletes its temporary directory): spool write time per slice, the commit against `18 microseconds * rows`, the peak memory of the call that commits against a one-shot re-index, the peak extra disk (spool, database growth, journal, temporary file) and the first audit after the re-index against the first one after a cold sync; the numbers are in the pull request. `tests/test_reindex_equivalence.py` re-indexes the same synthetic session in one piece and through the spool in many small slices (all five parsers; a parser upgrade, a changed word, changed AGY receipts; blocks across 1 MiB boundaries; an audit of each) and compares event ids and data, cursor, block table, metrics, AGY dependencies and tallies, journalled deletions and the generation; `test_reindex_faults.py` stops a staged re-index at every one of its cooperative checks (all of them for Codex, a sample for the others) and kills a process after the row frames, after the trailer, with the spool complete, inside the commit transaction and after the commit; a request stopped right after a spooled slice, or after the commit that published the re-index, loses its answer and nothing else; `test_reindex_staging.py` covers a spool that no longer matches (source changed in the head and in the middle, target version moved, another process finished, cursor rewritten, no room, receipts), torn writes, the commit that does not fit (`ready_to_commit`), privacy and the cases that never stage; `test_reindex_convergence.py` re-indexes a 150,000-event session with budgets of about 4 and 8 seconds on the development machine; the tests that run on the real clock take their budgets from the time the one-shot re-index took on the machine that runs them (and the commit prediction from the commit rate measured there), so that a sanitizer build, which is three to four times slower, gives the same answer. The new tests run in the smoke job and the Linux regression job.
- **An audit of a big session converges: a slice is sized by what judging it costs, and a comparison never takes the answer with it** ([#26](https://github.com/fox1245/tsukkomi-mcp/issues/26), roundtable 8, PR4). Slice commits made the sync keep its progress; the judging that follows was still all or nothing under the same deadline, so an evaluation that the deadline cut saved nothing and the next call started it again. On a synthetic Codex session judged by eighteen heavy contracts (judging an event costs about as much as syncing it), all of 14 consecutive `audit_session` calls with the 8-second hook budget ended `request_deadline` at 150,000 events and at 300,000, the sync moving all the while. The same calls now reach the complete answer, equal to the unbounded one finding for finding, in 3 and in 6 calls, none longer than 6.5 s. For two and for six contracts nothing was cut before and nothing changes (3 calls at 150k and 5 at 300k, none longer than 4.2 s). The numbers and the method are in [Large sessions and deadlines](README.md#large-sessions-and-deadlines).
  - **A slice is sized by what judging it costs.** For `audit_session` and `check_action` the share of the request (PR2: `0.5 * remaining / 1.3` of the sync's 60 %) is now only the upper bound. The parse also ends at the same record boundary, at the same clock reads (nothing reads the clock more often), once `time spent * 1.3 + records read * expected seconds to judge one record` reaches 85 % of the request's time, less the judging of the events the index already holds without a monitor state (`debt_events`). The parse speed in that sum is the one the slice itself shows; the minimum progress (256 records and 1 MiB) still holds. What judging costs is a moving average per contract set kept in memory by the process (`eval_cost.py`: smoothing 0.3; the first measurement replaces the prior; a fold the deadline stopped counts too; measurements over fewer than 2,000 events and folds in which only some monitors took part are not used): before a set was measured 60 microseconds an event, more for many contracts (12 + 4 per contract that needs history, when that is more), and half as much again, since a committed slice cannot be cut again. It is nothing when no contract needs history (a `check_action` against prohibitions), and `SELF_DIRECT_AUDIT_INCREMENTAL=false` keeps the slices of the share alone. A parse shorter than the minimum progress never reads the contracts for it, so the small append of a hook pays nothing. Only a slice that is appended to the index is sized this way. A slice of a staged re-index (previous entry) is judged by nobody until it is published, the audit after it reads the old index, so it keeps the share alone, never reads the contracts or the index for numbers, and its `cost` says `eval_us` 0; the commit that publishes a re-index is not a measurement of what an appended event costs and the model does not learn from it.
  - **A comparison never takes the answer with it.** The warm-up comparison used to run in the same pass as the answer under the same deadline: on a heavy contract set the first call of a cold session spent on it the room its answer needed and ended as `request_deadline`, saving nothing. Now the incremental answer comes first. A planned comparison is skipped when it cannot follow it in half of the room that is left (`incremental.comparison_shortfall`: a full evaluation costs about 1.5 folds an event, margin 25 %), before its events are read when this process has measured the contract set, and again after the pass from the speed that pass folded at (`shadow_skipped: "deadline"`); one that starts and does not finish in the room it has is cut and the answer stands, unverified, with its states saved. Where a resident engine's idle comparison exists the skip says `"deferred"`: the comparison is owed (the warm-up count does not move) and the idle comparison makes it. A skipped comparison is not asked for again by the second pass a violation calls for (that pass would fold everything again with less time). The checks only skip more than the estimate (`_shadow_affordable`) that was there; the schedule (rates, warm-up count, forced reasons) and what a comparison verifies are unchanged, and a comparison that an answer called for keeps its own pass and fallback. Measured: with 300,000 events and eighteen heavy contracts the 45-second calls took 44.8 and 23.2 s and now take 23.6 and 6.5 s.
  - **An index with no monitor state.** A state is valid only at a logged commit, and a session indexed in one piece has none inside it: one request has to fold all of it (0.4 s per 150,000 events for two contracts, 1.4 s for six, 7.0 s for eighteen heavy ones). Folding in chunks between commit boundaries was measured and not built: the commit log keeps 256 commits, and for a session that grew by a hook sync after every six events they span the last 7.6 % of 20,000 events. A fold that does not fit leaves `request_deadline` as before; what changed is the way out. A stopped audit is noted to the idle comparison of a resident engine, which audits the session with the budget of a background job and keeps the states (only a deadline, not a cancellation, is noted): in the measurements an 8-second call that was cut was followed by a call of 0.1 s with the complete answer. Without one, `audit_session` with a larger `timeout_ms` builds the states once. Adding states at offsets the commit log does not hold was not done: it changes the lineage rules. A published re-index starts a new generation of the session and drops the states of the old one, so the first audit after a re-index is this case as well; the idle comparison covers it, and a deadline that merely ended a staged slice (a partial result is an answer) or the sync before anything was judged is not noted to it.
  - **Response, additively.** A partial `audit_session`/`check_action` carries the `sync` object; every `sync` gains `cost` = `{slice_us, eval_us, debt_events, limited_by: "share" | "cost" | null}` (a staged re-index reports `reindex` and `cost` side by side, with `limited_by` of `share` or `null`). `audit_status` gains `evaluation` = `{cost: {slice_us, defaults_us, eval_sets_measured, eval_us_median}, session: {events_indexed, events_without_state, states_through_byte}}`. `incremental.shadow_skipped` may say `"deferred"`. No setting was added; no existing field changed. `SessionStore.audit_progress` and `audit_debt` read the lag (states held in memory by a resident engine count).
  - **Measured and tested.** `scripts/bench_eval_converge.py` (synthetic, seeded, deletes its temporary directory; it also runs on a checkout without this change, which is how the "before" numbers were taken): K, the seconds of every call and whether the final answer equals the unbounded one, for two, six and eighteen contracts, 150,000 and 300,000 events, 8 and 45 seconds, cold and synced, and with a resident engine's idle comparison. `tests/test_eval_converges.py` runs the real engine on a small session in virtual time (`tests/convergence_support.py`: a price per parsed record, folded event and full evaluation; the request deadline, the soft deadline and the room for a comparison read that clock), so the calls, stops and answers do not depend on the machine; two tests are controls that fail without the change (the heavy regime with the share alone loses calls; a slice sized without the debt does not fit). `tests/test_eval_cost.py` covers the model and the bound. `tests/test_eval_reindex.py` pins how it fits with the staged re-index: a staged slice never consults the sizing, the appended slice of the same session afterwards is cost-limited, the commit of a re-index teaches the model nothing, and the idle worker is told about a stopped evaluation only (scripted clocks, no wall clock). The warm path of small sessions (`scripts/bench_warm.py`) is unchanged within noise.
- **Public tree cleanup**: the setup skill clones the public repository instead of a private predecessor, the historical timeout report no longer names an unrelated private project, and the Grok Bot fixture session uses a clearly synthetic id.
- **Request statistics, and an `audit_status` that answers while the engine is busy** ([#26](https://github.com/fox1245/tsukkomi-mcp/issues/26), roundtable 8, P6). New `request_stats.py`: process-wide counters behind one short lock that never touches the engine, its lock or the index. Per tool (the registered tool names, and `hook` for the Codex hook tool): the number of calls, how they ended (`ok`, `degraded`, `incomplete`, `client_cancelled`, `error`), the reason of an `incomplete` or `degraded` end (`request_deadline`, `index_busy`, `request_cancelled`, `operation_timeout`, `sync_deadline`, `sync_in_progress`, `other`) and fixed-bucket histograms, in milliseconds (50, 100, 250, 500, 1000, 2000, 4000, 8000, 16000, 45000, +inf), of the elapsed time and of the wait for a heavy-call slot, with their maxima. Per process: the workers a deadline left running (`abandoned_now`, `abandoned_total`, `late_finish_total`) and the heavy-call gate (`slots`, `in_use`). A request is counted once, at its response; the late end of an abandoned worker is counted only in the worker numbers. Every label comes from a closed set (anything else is `other`); nothing else is recorded (no session id, path, contract text, argument or exception message), and nothing is written to disk or kept across a restart. `audit_status` attaches the snapshot as `ops` to its answer **whatever its kind**, including an `index_busy` or `request_deadline` answer, so it can be read while another thread holds the engine lock. The daemon's engines share the process's statistics. Command hooks that bypass the MCP dispatcher and the `workflow_*` tools are not counted.
- **Judging continues when the sync runs out of its share of the time** ([#26](https://github.com/fox1245/tsukkomi-mcp/issues/26), P4-1). A `check_action` or `audit_session` with a deadline gives its evidence refresh 60 % of the time left (`SYNC_BUDGET_SHARE` in `engine.py`) and keeps the rest for judging. When the refresh does not finish in its share and the request itself is still live, the stored index is judged instead, the way a sync that failed for another reason already was, and the answer says so: `coverage.complete` is `false`, `coverage.issues` and `integrity.reason` name `sync_deadline`. A proposed action that matches a `must_not` regex (for `audit_session`: a match in the stored events) is a `violation` although the sync did not finish; everything else is `unknown` at best (the extra issue keeps `judged_prefix`, and so a `clean` as of the cursor, impossible), and a `must` obligation that rests on missing evidence stays `unknown`. Before, the deadline of the sync was the deadline of the request: a cold sync that could not finish ended the whole request as `request_deadline`, and the checks that need no history were lost with it. Such an answer is counted as `degraded` / `sync_deadline` in the statistics. With slice commits (below) a sync of a plain session file stops at its soft deadline inside its share and keeps what it parsed, so this fallback is left for the syncs that cannot slice (a re-index, a `.jsonl.zst` source, `SELF_DIRECT_SYNC_SLICING=off`).
- Tests: `tests/test_request_stats.py` (counters, buckets, folding, snapshot shape, thread safety, no content), `tests/test_degraded_evaluation.py` (the fallback and what still propagates: the request's own deadline, a client cancellation, a busy index, `sync_session`) and `tests/test_server_ops.py` (one count per request, `ops` on every kind of `audit_status` answer, the timings of an incomplete answer), all in the Linux regression job of the CI.

### Changed

- **Preparing a graph batch costs the batch, not the session.** `run_neograph_update` captured the whole session and parsed every event on every call, then kept at most 100. `SessionStore.event_frames_range` steps over the events before the cursor in the `events_session` index and parses only the batch (and the one event that did not fit); `run_neograph_update` and `graph_next_batch` both read through it with the same limits, masking, `graph_event_too_large` behaviour and `remaining_events` meaning. On a synthetic session of 70,000 events (61 MB of text), no model call: 0.7 to 0.8 s per batch before, 14 to 25 ms after (the deeper the cursor, the more index entries are stepped over), peak memory 365 MB before and 63 MB after; the batches are identical at nine cursor positions. A regression test counts parsed events instead of time (20,000-event session: 100 parsed, 20,000 before).
- The extractor prompt and the proposal schema are one constant each, `neograph_runner.EXTRACT_INSTRUCTIONS` and `PROPOSAL_SCHEMA`, shared by the OpenRouter request and `graph_next_batch`. The schema is byte-identical to the one the request always sent. The prompt is not: it gained one sentence, see the next entry.
- **Node ids, kinds, labels and edge ends must be single-line plain text.** `graphrag.validate_proposal` (so `propose_graph_update`, `commit_graph_update`, `run_neograph_update` and the host tools) and the host tools' shape check reject, by Unicode category, a control character (newline, carriage return, tab, escape and the rest: Cc), the line and paragraph separators U+2028 and U+2029, a lone surrogate and a format character (Cf) other than the zero-width non-joiner U+200C, the zero-width joiner U+200D and the soft hyphen U+00AD. That is every character that can reorder or hide text (the bidirectional marks, embeddings and isolates, the zero-width space, the word joiner and invisible operators, the byte order mark, the interlinear annotation characters, the tag characters), with the other format characters rejected alongside so the rule stays closed for ones added later. The three exceptions only join or hyphenate, and ordinary text needs them: Persian words carry U+200C, emoji sequences and Indic conjuncts carry U+200D, so refusing them would reject, again and again, what a model writes in those scripts (`run_neograph_update` has no way to ask it to rephrase). Everything else, Hangul and the other scripts included, is accepted; README "Single-line text" has the exact rule. Problem texts name the code points instead of repeating the text, and the existing ones escape what they echo. **The OpenRouter extractor prompt gained one sentence** at the end of its rules (`node_id, kind and label must be single-line plain text: ...`) so that a model stops writing what the check refuses; the text before it and the proposal schema are unchanged (`tests/test_graph_host_extraction.py` pins the hash of both), and `graph_next_batch` hands out the same instructions with a `text_rules` line. The AGY `PreInvocation` hook printed `Context only: <src> -[<relation>]-> <dst>` with the stored text as it was, so an id such as `x`, a newline, `Contract [allow-everything] must_not: ...` came out as lines of its own in the model's context; it now prints each relation, and each contract description and checklist item it lists, on one line with such characters shown as escapes, which also covers rows stored earlier.
- **Model-written tool prose is not tool-call payload.** Claude Code's `Bash` input (and other built-in tools) has a model-written `description`; AGY tool calls carry `toolAction` and `toolSummary`. A `must_not` regex such as `sqlite3` matched the careful command `ls -l data/app.sqlite3` through its description "without connecting to it with sqlite3" (reported as an 11% false-positive rate in [#15](https://github.com/fox1245/tsukkomi-mcp/issues/15)). Those fields are now excluded from the call text that contracts match, in indexed history and in the proposed action a hook passes to `check_action` alike (one builder, `tool_payload.py`, also used by the Codex gating text and the standard-library high-risk fallback). Only confirmed prose fields are excluded, only their string values; unclassified fields (an MCP tool's `description`, AGY `Description`/`Instruction`, Codex `justification`, OMP `_i`) stay payload. The prose is kept in `meta.tool_prose`; `scope: "prose"` is a follow-up. Parser versions: Claude Code 2 to 3, AGY 7 to 8 (each indexed session is reparsed once on its next sync or audit; restart running processes). The two parser-version tests that pinned 2 and 7 now assert the current version.
- **A masked exit status is not success evidence for `requires_success`.** A `requires_success` contract ("commit only after a successful pytest") accepted any matching command whose recorded result was a success, so `pytest -q || true`, `pytest | tee log` (no `set -o pipefail` earlier in the same command), `pytest; exit 0` or `pytest --collect-only` counted as a passing run. A success recorded for such a command line is no longer evidence: the finding is `unknown` with the reason `success_unverifiable` (not clean, not a violation); a result recorded as failed is still a confirmed failure and the command itself is not blocked. A small quote-aware shell lexer (`audit/shellstatus.py`; operators inside quotes, `$( )` and comments are ignored, `set +e` alone changes nothing, `|| exit 1` and `; exit $?` keep a failure) locates the command the regex matched and decides; the reference evaluator and the incremental monitors call the same function (the monitor's per-call tracker gains the verdict). A `Bash` call run with `run_in_background` is not a success either (its result only says it started). `EVALUATOR_VERSION` 2 to 3, and to 6 once the anchor, refusal and background changes below are counted (stored monitor states are rebuilt once). The differential test generator now emits masking tails.
- **A contract's `source_event_id` must be a user message; weakening a contract needs one.** An audit now makes a contract whose `source_event_id` resolves to a non-user event (a tool result, runtime text, injected context) `unknown` with the reason `anchor_not_user`, in the reference evaluator and the monitors alike (`applies_from_event_id` may still be any event). `upsert_contracts` rejects such an anchor with an error when the event is already indexed and accepts an unresolvable one (the audit decides); its response reports `anchor_checks`. Disabling a contract (`revoke_contract` now takes `source_event_id`) or replacing it with one that may enforce less (a different regex, an added or changed exception, a narrower scope, roles, `when`, provider or session, dropping `requires_success`, lowering `risk`) needs an anchor that resolves to a user message; without one the change is stored as `pending` (a new key of the contracts file, omitted while empty; shown by `list_contracts`), the previous revision stays active and the response says `NOT APPLIED`. A later anchored upsert or revoke applies it. No origin field was added to the stored contract: `ContractRule` rejects unknown keys, so older processes would refuse the file. The user-message test is each parser's `role == "user"`; Codex cannot distinguish typed prompts from user-role injected context. `EVALUATOR_VERSION` 3 to 4. Existing tests that replaced a regex or revoked a contract without an anchor now pass a user anchor.
- **A refused tool call is a rejected proposal, not an executed violation.** Claude Code records the host's permission decision on the record of the tool result: a top-level `permissionDecision` object beside `toolDenialKind`, with an error result (verified against Claude Code 2.1.299 with a synthetic probe, a `PreToolUse` hook answering `deny` for `Bash`). A `must_not` match in a call whose linked result carries `{"decision": "reject", ...}` (whatever its `source`) or the forms `"deny"` / `{"behavior": "deny"}` is no longer an executed match: it is reported in the new `proposals_rejected` list of the finding (`contract_id`, `event_id`, `call_id`, `reason`, `denied_by` (the decision's `source`, or `host`), `denial_event_id`, `at_byte`; omitted while empty), the verdict comes from the remaining evidence (`clean`, reason `no executed forbidden match ...`, when all matches were refused) and an `exception_regex` sees only what ran. A result that merely says error, an `accept`/`allow`/`ask` decision, or an unknown or missing decision is still an attempt; `toolDenialKind` is not read; an id shared by several calls vouches for none. AGY's denied model proposals (already excluded from attempts) are now listed too. Codex, OMP and Cursor / Grok Bot have no reliable host-recorded denial. The Claude Code and AGY `Stop` notes show rejected proposals on their own line, apart from unverified checks and executed violations. Both evaluators implement it (`runner.rejected_calls`, the monitors' `ClaudeFacts.rejected` and per-rule matching-call table; Claude Code `must_not` audits now keep a call-id index and the shared facts state); the audit-event loader reads `permission_decision` for Claude Code. `EVALUATOR_VERSION` 4 to 5 (and 7 once the recorded decision shape below is counted). No parser change.
- **Format drift makes history absence proofs unknown at the finding level too.** With incomplete coverage other than pure append (an unsupported record, a parse error), the overall verdict was already `unknown`, but a `must_not` with no parsed match and a `before_regex` rule with no parsed trigger still said `clean` in their findings. They are now `unknown` (`incomplete evidence cannot prove the absence of a forbidden match` / `... that no triggering action occurred`); a confirmed violation stays a violation, `judged_prefix` (appended bytes only) behaves as before and a proposed action is judged on its own text. `tests/test_format_drift_coverage.py` locks in the behaviour for Claude Code, Codex and AGY.
- **AGY hooks cost what was appended, not the size of the transcript.** A PreToolUse or PostToolUse hook parsed the whole transcript several times (for the anchor and the completed results of its receipt, again when a sync bound the receipt, and again to index it, because every receipt change reparsed the conversation) and hashed the prefix once more for every linked result, so one hook cost O(size) in Python and a first parse O(linked results x size) in SHA-256. Now: (1) a receipt hashes the file once and parses only the records after a prefix verified against the stored SHA-256 (a per-conversation, per-file ledger in `agy-receipts.sqlite`: `scan_state`, `scan_results`; a cache of a parse, used only after the digest of its prefix was recomputed from the file in the same pass, falling back to the whole-file parse on any doubt, a step the transcript already reached, a repeated result or an error); (2) the sync's capture pass keeps a hash state at every receipt's `prefix_length`, so each anchor (still the plain SHA-256 of the file's bytes; AGY is never verified with block digests or samples) is read from that pass; (3) the index stores with the cursor (`session_receipt_deps`) the digest of the receipt of every result step it parsed and the first receipt, which are the only things the parse reads from receipts, and a receipt change reparses (`reindex_reason: "hook_receipts_changed"`) only when it changed one of those for an indexed result: a receipt for a step with no result yet, the usual `PreToolUse`, is a plain append (an index without stored dependencies reparses once, on its next receipt change); (4) `prepare_bindings` scans only for receipts that are unbound and name the file, reads receipts lazily, and `rows_digest` of unchanged rows is not recomputed; (5) the parser rules out undecodable bytes with `str.isascii` and one regex search instead of a Python loop over every character, and resolves the transcript path once per parse. Receipts, chunks, evidence stats, coverage and verdicts are unchanged (`tests/test_agy_append_equivalence.py` compares an index kept by appends, hooks and syncs with a fresh reindex of the same files and receipts). Measured with `scripts/bench_agy_hooks.py` (synthetic transcripts with a linked receipt per result, one hook per fresh process): at 10 MB a `PreToolUse` hook (receipt and contract check) fell from 20.5 s to 0.51 s and a `PostToolUse` hook (receipt and sync) from 20.4 s to 0.58 s, against 0.38 s and 0.36 s at 0.1 MB; the transcript-dependent part left is two SHA-256 passes and per-receipt work in C. The first hook after an upgrade parses the whole file once. See [AGY hook cost](docs/agy-installation.md#hook-cost-what-a-hook-reads).
- **A request scans the source prefix once.** One `check_action` on a 300 MB session hashed the whole prefix five times (the capture pass and four later re-checks); it now hashes it once, in the capture pass. `validate_prefix()` re-checks file identity, `size >= captured length` and the SHA-256 of the last 64 KiB as streamed during the pass; an unchanged size with a moved modification time is settled by a re-read of the prefix; `validate_prefix(full=True)` is the explicit whole-prefix re-read. If the file grew while it was hashed, the bounded check replaces the second scan. ### Fixed

- **`commit_graph_update` stored nothing after its first call when it was given no `job_id`.** Every such commit was the global job `adhoc`: the first one, in any session, recorded it as applied and every later one, in any session, answered `already_applied` and stored nothing; the documented `through_order` path was caught by it. A commit without a `job_id` is now named by provider, session, the event order it moves the cursor to (its `through_order`, or the end of the session as it stands: the id is derived after that is resolved) and a digest of the proposal (`adhoc-...`): the identical call again at the same place is `already_applied`, any other commit applies, the same proposal after the session has grown included.
- **A job id recorded for another session counted as an applied job.** The storage-level replay guard looked jobs up by id alone and `record_job` replaced whatever row held the id, so a batch whose id had been recorded by a commit in another session answered `already_applied` and stored nothing, for ever. The guard is now scoped to provider and session: another session's id is `job_id_in_use`, nothing is written and the other row is never overwritten.
- `propose_graph_update` and `commit_graph_update` report `covers_through_order` also when they answer `version_conflict` or `evidence_conflict`.
- **Lookups of stored events by id no longer scan the whole session.** `SessionStore.live_ids` and `capture_evidence(history=False, anchors=...)` select from `session_events` by `provider`, `session_id` and a list of event ids. Without table statistics SQLite chose the two equalities over the primary key, so every 500-id batch read the entire session and a derived pass (the search index that `sync_session` and `search_history` build) cost the square of the session size. The equalities are now written `+provider=? AND +session_id=?`, which keeps the planner on the key. The commit of an append asks the same question for the ids it brings, so a large append to a large session paid it too. On synthetic Linux sessions the derived pass over 90,000 events went from 29.3 s to 7.1 s (profiled) and over 150,000 events from 64.2 s to 7.7 s, and appending 100,000 events to an indexed session of 100,000 from 12.7 s to 3.4 s. Appends of a few events were never affected (SQLite already used the key for short lists). `tests/test_event_id_lookups.py` pins the query plan.

## 0.6.0 - 2026-10-14

Merged in [PR #7](https://github.com/fox1245/tsukkomi-mcp/pull/7) and [PR #11](https://github.com/fox1245/tsukkomi-mcp/pull/11). PR #7 also carried the unmerged commits of the AGY and workflow branch. The Claude Code integration, the shared hook policy, the masking work and AGY parser versions 6 and 7 were added to this release afterwards. Read "Upgrading to 0.6.0" in the [README](README.md) before restarting existing servers: restart every process that shares an index.

### Upgrade-relevant changes

- `neograph-engine` is pinned to `0.14.1` (was `0.12.1`).
- Python before 3.14 now depends on `zstandard>=0.23` to read compressed Codex sessions. Python 3.14+ uses the standard library `compression.zstd`. Without a zstd module, compressed sessions report `zstd_unavailable` and plain sessions are unaffected. Restart existing servers after updating so they can read `.jsonl.zst` rollouts.
- The default index directory is `~/.self_direct_index` (was `.self_direct_index` inside the checkout). Installs that relied on the old default must set `SELF_DIRECT_INDEX_DIR` or TOML `index_dir`; nothing is moved automatically.
- A checkout `.env` is no longer selected as an authoritative key file. Use `SELF_DIRECT_OPENROUTER_API_KEY_FILE` or TOML `openrouter_api_key_file`. A plain `.env` is read only from the server's working directory.
- Parser versions: OMP 2 to 8, Codex 2 to 3, AGY 5 to 7, and the new Claude Code parser at 2. Each indexed session is reparsed lazily on its next sync; existing indexes, vector caches, contracts and checklists are preserved.
- The AGY hook default is now `confirmed_only` (it was `enforced`). Only a confirmed `violation` denies and `suspicious` force-asks; `unknown` passes with a visible warning unless a contract is marked `risk: "high"`. Set `SELF_DIRECT_AGY_ENFORCEMENT=enforced` to keep a strict policy. A `Stop` now continues the agent only for a confirmed `auto_continue` miss, at most once per conversation, and hook errors fail open in every mode (they used to fail closed for `PreToolUse`) ([#1](https://github.com/fox1245/tsukkomi-mcp/issues/1)).
- Sparse (FTS) rows written before 0.6.0 hold raw text. Delete `sparse.sqlite` while the servers are stopped to rebuild it masked from the canonical store (see the [masking contract](SECURITY.md#masking-contract)).

### Added

### Changed

- Source capture streams a SHA-256 over the file up to its first-measured length and keeps no bytes. `validate_prefix()` tolerates pure growth after re-hashing the prefix; `validate()` is metadata only. `stat` and `fstat` stamps are compared within the same API, and an `st_ino` of 0 (some Windows filesystems) skips the inode comparison ([#4](https://github.com/fox1245/tsukkomi-mcp/issues/4), [#5](https://github.com/fox1245/tsukkomi-mcp/issues/5)).
- Audits judge a growing session as of the captured offset and say so in `coverage` and `notes`. `must` obligations that rest on absent or failed evidence become `unknown` while bytes are unread. Rewrites, truncation, replacement and deletion stay `unknown`. `requires_attention` follows the verdict ([#4](https://github.com/fox1245/tsukkomi-mcp/issues/4)).
- `check_action` keeps a proposed action's `requires_success` prerequisites `unknown` while required history is unread ([#8](https://github.com/fox1245/tsukkomi-mcp/issues/8)).
- Memory and concurrency: single-flight per (index, provider, session id), streaming reparse through a disk spool with batched publication, per-session id queries, float32 sync vectors, slimmer audit row loading, and `malloc_trim` on glibc after heavy calls ([#5](https://github.com/fox1245/tsukkomi-mcp/issues/5), [#10](https://github.com/fox1245/tsukkomi-mcp/issues/10)). On a 100 MB synthetic OMP session with 8 concurrent threads, peak RSS fell from 2,304 MB to 193 MB ([PR #7](https://github.com/fox1245/tsukkomi-mcp/pull/7)).
- `audit_status` counts sparse documents from `chunk_rows` instead of scanning the FTS5 table ([#5](https://github.com/fox1245/tsukkomi-mcp/issues/5)).
- Shared-index snapshots and cooperative request deadlines; `index_busy`, `request_deadline`, `request_cancelled` and `operation_timeout` are distinct results ([#3](https://github.com/fox1245/tsukkomi-mcp/issues/3)).
- OMP parser v8 accepts host notices, image placeholders, steering records, `session_init`, `model_usage`, `branch_summary` and `redactedThinking` as runtime records. Only `attribution: "user"` steering is a user turn; agent-attributed user-role messages are runtime text ([#9](https://github.com/fox1245/tsukkomi-mcp/issues/9)).
- A rollout file name that contains two different UUIDs (the `_<uuid>` suffix form) no longer names a session by itself; the `session_meta` header decides. Session lookup by id prefers a plain `.jsonl` over its compressed twin.
- Codex parser v3 accepts `agent_message`, `inter_agent_communication_metadata`, `tool_search_call`/`tool_search_output`, the newer `session_meta` fields and inherited parent headers. `base_instructions`, `dynamic_tools`, account ids and tool lists are never indexed ([PR #11](https://github.com/fox1245/tsukkomi-mcp/pull/11)).
- AGY advisory mode no longer gates approved workflows: in `advisory`, `PreToolUse` allows a mapped completion action with an advisory reason and `Stop` does not hold an incomplete workflow. In the other modes the workflow hold shares the once-per-conversation budget.
- `get_settings()` no longer loads the selected key file into `os.environ`, where subprocesses and native hosts would inherit every variable in a shared file. sqlite-vector auto-detection also checks the setup script's `.native/` default, the sdist ships `CHANGELOG.md` and `SECURITY.md`, and the setup skill no longer suggests a fake embedder as a fallback when a key is missing.
- `when` gates `must` obligations that are checked against a proposed action, and a `not_applicable` finding that late incompleteness turns `unknown` no longer keeps its applicability. Healthy hook-state reads take no write lock, and concurrent continue claims spend the budget exactly once.
- Masking is faster (per-stem rules, static templates and an ASCII mode).
- Tests: symlink tests report a skip with a reason where Windows denies symlink creation (`WinError 1314`, Developer Mode off); the installer quoting and the dotenv JSON fixture are platform-aware.
- OMP history retrieval uses OpenRouter by default; offline mode is the explicit `SELF_DIRECT_LOCAL_ONLY=true`. Session evidence is masked before remote graph extraction, and workflow classification uses the shared OpenRouter key settings.

### Fixed

- Contract regexes run with a time limit (`regex` engine, new dependency): 0.25 s per search, 2 s per contract per evaluation. A pathological pattern used to backtrack for minutes, past the audit deadline and a host's hook timeout, after which the host proceeded with the call. Such a contract is now `unknown` (`regex_timeout`); `search_history` regex queries report the limit instead of partial results.
- Codex `PreToolUse` no longer reports an empty-findings `unknown` when no contract applies to the proposed action (`action_scope: not_applicable`), matching the AGY and Claude Code adapters.
- Masking now covers common credential names it missed: `*_PASS`, `*_PWD`, `PASSPHRASE`, `*_KEY`, `*_KEY_ID`, `*_SALT`, `PEPPER`, `*_AUTH`.
- `upsert_contracts` rejects a high-risk `must_not` without a regex (it would ask on every tool call) and validates `exception_regex`.
- The allocator trim after heavy calls now counts the heavy work done since the last trim, not the length of one call. A server that mostly answers short hook checks never had a single call long enough to trim, so freed heap stayed resident; it now trims at most every 5 seconds once 0.5 seconds of heavy work has accumulated. In the soak, live native allocations stay flat as history grows; the remaining RSS growth is allocator-retained memory.
- A local-only process sharing an index that has dense vectors (for example a lifecycle hook installed with `--local-only` next to a server with embeddings) now leaves the vector cleanup of obsolete chunk ids journalled instead of acknowledging it. Before, a reparse in that process removed the ids from the sparse index only, and their vectors stayed orphaned for good. The next sync by a process with the dense index removes them.
- AGY hooks in `advisory` mode no longer deny or continue on an internal exception, in `agy_hooks.main` and in the fallback script.
- Sync no longer fails with `source changed during preparation` when records are appended during capture ([#4](https://github.com/fox1245/tsukkomi-mcp/issues/4)).
- Equal file stamps no longer skip content verification, and a detected mismatch stays failed ([#8](https://github.com/fox1245/tsukkomi-mcp/issues/8)).
- A stale capture can no longer rewind a cursor that another process already published ([PR #7](https://github.com/fox1245/tsukkomi-mcp/pull/7)).
- Unbounded memory growth in long-running servers ([#5](https://github.com/fox1245/tsukkomi-mcp/issues/5)).
- Concurrent `update_checklist` and contract updates no longer fail with stale-preparation errors ([#6](https://github.com/fox1245/tsukkomi-mcp/issues/6)).
- Agent-attributed messages with partial steering metadata were treated as user turns, and payloads of unsupported image and `redactedThinking` blocks were indexed ([#9](https://github.com/fox1245/tsukkomi-mcp/issues/9)).
- Files with the same session id in different folders caused a full reparse on every sync ([#10](https://github.com/fox1245/tsukkomi-mcp/issues/10)).
- Real Codex sessions no longer report most records as unsupported or as parse errors; in a 571-session check, v2 showed unsupported events in 401 sessions and parse errors in 121, and v3 showed none ([PR #11](https://github.com/fox1245/tsukkomi-mcp/pull/11)).

### Known limitations

- Capture and validation are not an atomic snapshot. A rewrite outside the last 64 KiB between the final full hash and the publication lock is accepted at that moment; the next sync reindexes because the cursor's prefix hash no longer matches.
- On Windows `st_ctime` is the creation time, so a same-size rewrite that restores `mtime` is invisible to `stat`; the next sync catches it through the cursor prefix hash.
- `clean` for a growing session means clean as of `judged_through_byte`. Records appended during the audit are judged by the next audit.
- Memory with a live ~310 MB session was not measured before release.
